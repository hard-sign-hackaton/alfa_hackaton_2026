# Банковские источники в исследовании компании

Агент использует `BankReader` из `research/ai/bank_repository.py`. Он читает `analytics_documents`, `analytics_chunks` и векторы из общего PostgreSQL, затем возвращает `RetrievedSource` с namespace `bank:`, названием отчёта, датой и страницами. `search_bank_analytics` делегирует поиск этому адаптеру. Старый поиск по `bank_analytics` сохраняется для отдельно создаваемых legacy-репозиториев без адаптера.

По умолчанию адрес берётся из `NEWS_DATABASE_URL`, опционально из `BANK_DATABASE_URL`. Для агента используются права SELECT. `news-db-init` создаёт роль и выдаёт чтение необходимых таблиц; импорт выполняется отдельной командой с правами записи.

`BANK_SEARCH_MODE`: `text`, `vector` или `hybrid`. Лёгкий агент по умолчанию использует текстовый поиск, `ai-agent-semantic` — гибридный. `BANK_EMBEDDING_PROFILE` выбирает сохранённый профиль; при нескольких профилях без явного выбора векторный поиск останавливается. Векторный поиск использует E5 query/passage и тот же immutable revision, что хранится в профиле. Гибридный поиск объединяет позиции векторной и текстовой выдачи с весами 2:1; максимум два фрагмента одного отчёта. Это порядок поиска контекста, не вероятность влияния.

## Импорт готового JSONL

Файл `chunks.jsonl` в корне исключён из Git и Docker build context. Compose-сервис `analytics` монтирует его отдельно только для чтения. Корпус можно загрузить без повторного OCR:

```powershell
docker compose build news ai-agent-semantic news-db-init
docker compose run --rm news-db-init
docker compose run --rm analytics import --chunks /input/chunks.jsonl --manifest /app/research/bank/manifest.json
docker compose run --rm analytics embed --revision 614241f622f53c4eeff9890bdc4f31cfecc418b3
docker compose run --rm analytics stats
```

Для отдельной исследовательской базы предварительно задайте `NEWS_DATABASE_NAME`; база должна существовать. Эти команды используют выбранную базу. Подготовленные компании и новости загружаются отдельно.

Импорт требует для каждого документа запись манифеста с названием и датой. Неизвестные документы, пустой текст, повторяющиеся ID и некорректный JSON отклоняются до записи. Markdown собирается из фрагментов и явно помечается как неполный. SHA-256 входного JSONL сохраняется отдельно и не выдаётся за хеш исходного PDF. Полные сетки таблиц и данные графиков не создаются; ссылки на таблицы и страницы сохраняются. Полная PDF-экстракция не заменяется частичным JSONL. Повторный импорт неизменённых фрагментов сохраняет рассчитанные векторы.

Если есть полный результат OCR, остаётся прежний интерфейс `analytics import --extracted ... --chunks ... --manifest ...`.

## Разбор и проверка

```powershell
docker compose run --rm --no-deps ai-agent-semantic --company-id U_128194 --news-id NEWS_ID --output /output/pair-with-bank
```

Агент выбирает запрос через инструмент `search_bank_analytics`; сначала проверяет платежные агрегаты и банковский контекст, затем дополнительные новости. Модели видят только возвращённые выдержки. Источники имеют стабильный текст между запросами, цитаты проверяются кодом, неизвестные источники и недословные цитаты отклоняются. Страницы и документ сохраняются также в `bank_metadata` результата.

Дата публикации фильтруется в SQL до ограничения выдачи. Старый обзор или прогноз банка не считается текущим фактом о компании. Дословность цитаты не доказывает обоснованность логического вывода. OCR может содержать ошибки, а отсутствие данных в отобранных фрагментах не доказывает отсутствие риска.

Проверочный прогон и отчёт:

```powershell
python scripts/run_bank_evaluation.py check --database alfa_research_20261022
python scripts/run_bank_evaluation.py analyze --database alfa_research_20261022
python scripts/run_bank_evaluation.py compact --database alfa_research_20261022
python scripts/run_bank_evaluation.py report --database alfa_research_20261022
```

`--reuse-preparation` для фазы `analyze` переиспользует проверенные классификации и извлечение событий из локального `dataset-final-20261022`, если этот прогон уже выполнен. Без флага выполняется весь модельный пайплайн. Успешные разборы кешируются в рамках версии пайплайна. Ключи и raw-ответы в Git не входят.

Результат: `research/evaluation/2026-10-22-bank/report.html`, `results.json`, `summary.json`. Три выбранных случая проверяют работоспособность интеграции, а не качество на независимой разметке. Предыдущие отчёты сохранены как результаты прогонов без банковского контекста.

## Короткие поля и классификация

Обычный `analyze_pair.py` сохраняет `brief.json` рядом с `result.json`; тот же объект находится в `result.json` в поле `brief`. Поля:

- `news_summary`: 1–2 коротких предложения о событии, до 360 символов;
- `short_answer`: краткий вывод для выбранной компании, до 360 символов;
- `classification.business_relevant` и `classification.topics`: результат классификации новости;
- `classification.importance`: `high`, `medium` или `low` для конкретной компании;
- `classification.importance_reason` и `importance_method`: обоснование и метод оценки;
- `evidence`: точные цитаты для сводки, вывода и важности.

Gemma через маршрут `brief` сокращает уже принятые утверждения и оценивает важность, выбирая их `claim_ids`. Код подставляет существующие цитаты; новых source_id модель не создаёт. Сводка новости ссылается только на факты исходной публикации. Вывод и важность требуют оснований из новости и данных компании. При недостаточных данных метка `high` отклоняется. Это качественная модельная оценка, не вероятность и не независимая валидация влияния.

Если модель краткого ответа недоступна, возвращаются выдержки из принятых утверждений со статусом `partial`; важность остаётся `null`. Неделовые новости исключаются правилом с меткой `low` и методом `rules`. Модель настраивается через `LLM_BRIEF_MODEL`; по умолчанию `google/gemma-4-26b-a4b-it`.

Контракт: `research/contracts/t01/compact-result.schema.json`. Для карточки интерфейса `news_summary` соответствует `event_summary`, `short_answer` — `effect_title`, а `classification.importance` — `importance`. Исходные контракты карточки и полного Insight сохранены.
