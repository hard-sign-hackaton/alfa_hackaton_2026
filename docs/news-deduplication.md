# Дедубликация при сборе новостей

`NewsIngestionService` сохраняет статьи через `NewsRepository.save_deduplicated()`.
Для нового URL сравниваются статьи всех источников с временем публикации
в пределах ±48 часов включительно, в том числе из предыдущих запусков.
Повторный URL остаётся обычным upsert; накопленные дубли не удаляются.

## Решение о дубле

1. Совпадение полного нормализованного текста — дубль без обращения к модели.
   Нормализация: Unicode NFC, нижний регистр, пробелы/переносы/неразрывные
   пробелы, типографские кавычки и тире. Исходный текст в БД не изменяется.
2. Для неточного совпадения требуется сходство символов **не ниже 0,85**.
   Используется `SequenceMatcher(autojunk=False)`: удвоенное число совпавших
   символов с учётом порядка, делённое на сумму длин нормализованных текстов.
3. Пара проходит консервативные лексические проверки. Последовательности
   чисел, имён с заглавной буквы и цитируемых названий должны совпасть.
   Проверяются отрицания, единицы измерения, даты и маркеры прогноза/решения,
   изменения и завершения события. Новое предложение не отбрасывается,
   даже если оно занимает меньше 15% статьи. Для каждого предложения нужно
   сходство ≥0,85; содержательные вставки/удаления и замены длиннее трёх
   слов оставляются отдельными публикациями. Короткие изменения формулировок
   и вводные связки могут пройти проверку.
4. Для прошедших кандидатов требуется косинусное сходство эмбеддингов
   **не ниже 0,97**. Только после этого публикация пропускается.

Заголовки могут различаться. Текстовый фильтр сравнивает тела; семантическая
проверка использует обычное представление новости (заголовок и полный текст).
Пороги — начальные консервативные значения, не оценка точности на реальных
данных. Лексические проверки не заменяют полноценное выделение сущностей
или проверку фактов: имена в нижнем регистре и неизвестные формулировки могут
не распознаваться. Разные пересказы, дополненные публикации и случаи сомнения
предпочтительно сохранять, поэтому часть перепечаток останется в БД.

## Эмбеддинги и переиспользование

Модель E5 загружается лениво, только при наличии кандидата после текстовых
проверок. Обёртка одна на сбор, с блокировкой доступа между потоками.
Неудачная инициализация не повторяется для каждой статьи того же сбора.
Применяются `NewsEmbeddingService`, его chunking, агрегация и профиль
`e5-title64-body384-overlap64-mean-l2-v1`, как на обычном этапе `embed`.

Вектор кандидата берётся из `news_embeddings` только при совпадении профиля
и `input_hash`. Если его нет, он считается и сохраняется. Вектор входящей
статьи считается один раз для всех её кандидатов. Если статья сохраняется,
её вектор записывается вместе с ней в ту же транзакцию. Если это дубль,
входящая статья и её вектор не сохраняются. Поэтому повторное поступление
ранее отброшенной неточной копии может потребовать нового вычисления.

Последующий `embed` с тем же профилем пропускает сохранённые валидные векторы.
Изменение текста/заголовка или профиля требует пересчёта. Для воспроизводимости
revision E5 можно закрепить существующим `NEWS_MODEL_REVISION`.
Если модель недоступна или вернула некорректный вектор, неточная копия
сохраняется; в отчёте появляется `deduplication_limitations` с причиной
`embedding_unavailable`. Точная дедубликация продолжает работать.

## Транзакции и отчёты

Сравнение, кеширование векторов и вставка выполняются под общей advisory-
блокировкой PostgreSQL. При READ COMMITTED ожидавший сборщик видит записи
предыдущего. Это защищает параллельные операции `save_deduplicated` и позволяет
им переиспользовать вектор общего кандидата. Парсинг и сбор HTML выполняются
до блокировки; первое обращение к модели, её загрузка и локальный inference
могут задержать другие сохраняющие потоки. Обычный `save()`, прямой SQL
и сторонние импорты не выполняют эту проверку. Независимый одновременно
запущенный `embed` не координирует вычисления с дедубликацией; переиспользование
гарантируется при последовательных этапах collect → embed.

Кандидаты выбираются по существующему индексу даты. Их тексты сравниваются
в Python; время проверки растёт с количеством публикаций в окне.
Первой записанной копии отдаётся приоритет. При нескольких уже существующих
совпадениях порядок выбора — `collected_at`, затем ID.

Пропущенная статья увеличивает `duplicates`, но не `saved` и не лимит
сохранений. `duplicate_matches` содержит URL копии, `original_id`,
`original_url` и причину `normalized_body_equal` либо `hybrid_text_embedding`.
Для гибридного решения добавляются `text_similarity` и `embedding_similarity`.
Источник только с дублями и без ошибок получает статус `completed`.

## Проверки

```sh
python -m unittest discover -s tests/news -v
```

Для интеграционных тестов задаётся `NEWS_TEST_DATABASE_URL` на отдельную
БД с окончанием `_test` и применёнными миграциями. Без переменной они
пропускаются. Тесты используют синтетические тексты, поддельные HTTP-клиенты
и детерминированный провайдер векторов без загрузки модели или сбора новостей.
Они проверяют полный путь collect → embed → export → search, фактическое
число вычислений, профиль/хеш, конкурентные копии и отказ модели.
